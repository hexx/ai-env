# 課題解決プロンプト: JINA_API_KEY をキーチェーンから取得し環境変数として渡す

## 1. 役割定義 (Persona)
あなたは高度なソフトウェアエンジニアおよび問題解決のエキスパートです。以下のコンテキストとゴールを基に、正確かつ効率的な修正/実装を行ってください。

## 2. 背景・前提条件 (Context)
- **現状発生している問題**: Apple Container 経由で起動するエージェントコンテナ内で `JINA_API_KEY`（Jina Reader / `web_fetch` や `llm_context` で利用）が設定されません。他の API キー（例: `BRAVE_SEARCH_API_KEY`, `OPENROUTER_API_KEY`）は macOS のキーチェーンから `security find-generic-password` で取得されコンテナへ `--env` 経由で渡されていますが、`JINA_API_KEY` はこの仕組みに含まれていません。
- **再現手順**:
  1. キーチェーンに `JINA_API_KEY` という名前（generic password の service 名）でトークンを登録している状態で、
  2. `index-helpers.ts` の `CREDENTIAL_SOURCES` を参照すると、`JINA_API_KEY` のエントリが存在しない。
  3. そのためコンテナ起動時の `runContainer` の `--env=JINA_API_KEY=...` が出力されず、コンテナ内で `JINA_API_KEY` が未定義となる。
- **関連ファイル/コード**:
  - `index-helpers.ts`
    - `CREDENTIAL_SOURCES`（約 L55〜L109）: 取得するクレデンシャルの定義配列。ここに `{ args: ["find-generic-password", "-s", "JINA_API_KEY", "-w"], file: "security", name: "JINA_API_KEY" }` を追加する（アルファベット順のソートルールに従い、`GH_TOKEN` の前、または該当する位置に挿入）。
    - `Credentials` / `PartialCredentials` 型（約 L110〜L118）: `CREDENTIAL_SOURCES` から自動導出されるため追加のみで型は自動拡張される。
    - `SECRET_ENV_PATTERN`（約 L120〜L128）: 末尾が `_API_KEY` で終わる変数は `JINA_API_KEY` も含め自動でマスク対象となるため、追加の正規表現変更は不要。
    - `runContainer` の `--env` 出力（約 L236〜L242）: ここに `--env=JINA_API_KEY=${params.credentials.JINA_API_KEY ?? ""}` を追加し、コンテナへ環境変数として渡す。
  - `index.test.ts`
    - `CREDENTIAL_SOURCES` の整合性テスト（約 L586〜L590 付近の describe ブロック）や `loadCredentials` が全ソースを取得するテスト（約 L527 付近）など、既存クレデンシャルを列挙・検証している箇所を `JINA_API_KEY` 追加に合わせて更新する。

## 3. 解決すべきゴール (Goal & Objective)
- [ ] `index-helpers.ts` の `CREDENTIAL_SOURCES` に `JINA_API_KEY` を `security find-generic-password -s JINA_API_KEY -w` で取得するエントリとして追加する（ソート/フォーマットルール `sort-keys` 等に従う）。
- [ ] `runContainer` の `--env` 出力に `JINA_API_KEY` を追加し、コンテナへ環境変数として渡す。
- [ ] `Credentials` 型が `CREDENTIAL_SOURCES` から自動導出されているため、型の不整合がないことを確認する（`JINA_API_KEY` が `params.credentials` で参照可能になること）。
- [ ] `SECRET_ENV_PATTERN` により `JINA_API_KEY` が stderr ダンプ時に `***` にマスクされることを確認する（末尾 `_API_KEY` ルールで自動カバー）。
- [ ] `index.test.ts` の関連テスト（`CREDENTIAL_SOURCES` 整合性、`loadCredentials` 全取得など）を `JINA_API_KEY` 追加に合わせて更新し、既存テストを壊さないこと。
- [ ] `oxlint` / `tsc` / テストがすべて通過すること。

## 4. 期待する成果物 (Output Format)
- 修正が完了した `index-helpers.ts` および `index.test.ts` のコード一式（または修正パッチ）。
- 修正理由とアプローチの簡潔な解説（なぜキーチェーン経由で取得し `--env` で渡すのか、`Credentials` 型は自動導出される点など）。
- `oxlint`、`tsc --noEmit`、および `node --test`（またはプロジェクトのテストコマンド）の実行結果。
