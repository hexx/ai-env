# グローバル CLI ツールは実行ユーザー領域（`~/.local/bin`）へインストールする

サンドボックス内で実行ユーザー pi が使う CLI ツール（pm2 / ctx など）は、
root 所有の `/usr/local` ではなく、pi が所有するユーザー領域 `~/.local/bin` へ
インストールする。

## 背景

Dockerfile で root のグローバルインストールしたツールを実行ユーザー pi から使う構成は、
以下の問題を繰り返し発生させた。

- **ctx の配置漏れ（2026-08-25, #128）**: root でインストールスクリプトを実行したため
  `$HOME/.local/bin` が `/root/.local/bin` になり pi の PATH から到達不能だった
  （コミット `68144a5` で `/usr/local/bin` 指定に修正）
- **pm2 の実行権限（2026-08-25, `85bc3c8`）**: root 所有の `/usr/local` にインストールした
  PM2 が pi から実行できず、起動スクリプトが停止（仕様 0003）
- **pm2 のビルド時検証失敗（2026-08-25）**: `command -v pm2 && pm2 --version` が exit 127 で
  失敗。dash の `command -v` は未発見時に exit 127 を返すため `pm2 --version` は実行されておらず、
  「PATH に見つからない」「壊れたシンボリックリンク」の区別がつかないままビルドを落としていた

根本原因は「root が所有するツールを別の実行ユーザーが使う」という権限の摩擦で、
chmod による事後調整（`85bc3c8` の実施内容）は対症療法に留まる。一方 herdr / rtk は
最初から `USER pi` 後に `~/.local/bin` へインストールされており、この種の問題を起こしていない。

さらに ctx.rs の公式インストーラは、インストール先ディレクトリを「実行ユーザー所有であること」
と「0700 化」を要求する単一ユーザー前提の設計に変更されており、root 所有の `/usr/local/bin` への
配置はインストーラの想定利用法に反する（`/usr/local/bin` 全体が 0700 になれば pi は
node / uv / pi を含む全てのシステム領域ツールを実行できなくなる）。

## 判断

- **実行ユーザー pi が使う CLI ツールは `USER pi` 後にユーザー領域（`~/.local/bin`）へ
  インストールする**
  - pm2: `npm install -g --prefix /home/pi/.local pm2@latest`
  - ctx: 公式インストーラを pi で実行し既定の `$HOME/.local/bin` へ（`CTX_BIN_DIR` 指定不要）
- **`/usr/local` はイメージ基盤系ツールに限る**（node / npm / uv / playwright /
  pi-coding-agent / open-code-review / hunkdiff）。これらは実行ユーザー固有の設定を持たず、
  root 所有のまま運用して問題が出ていない。
- **ビルド時検証は「実際に実行する」方式で行い、`command -v` での存在確認はしない**
  （dash が未発見時に exit 127 を返すため診断性が悪い）。

## 意図的な判断

- **採用: ユーザー領域インストール**: 権限調整（chmod）・PATH 前提・改ざん耐性の議論から
  ツールを解放する。herdr / rtk で実績のある既存パターンであり、単一ユーザーのサンドボックス
  における自然な形。
- **セキュリティトレードオフ（受容）**: pi 所有になるため pm2 / ctx を pi が改ざんできる。
  サンドボックスの実質的な信頼境界は「ホストが pi に何を渡すか」であり、pi は既に
  `~/.pi` / `~/.ctx` 等のホスト共有資産を所有している。root 所有の価値は
  「イメージが改ざんされるとサンドボックス全体が危険」な基盤系ツール（node / uv /
  playwright 等）に限定し、それらはシステム領域に残す。
- **棄却: root `/usr/local` に残したまま正しく直す**: 原因の特定と chmod の正しさに依存し、
  インストーラやベースイメージの変更で再発する（実際に `85bc3c8` で再発した）。
- **棄却: 検証ステップを緩める・撤去する**: 壊れたイメージを実行時まで残すことになり、
  実行時の縮退運用（仕様 0003）に依存を移すだけ。検証は残し、判定方法を変える。
- **uv とのパターン統合は誤解だった**: uv（astral 製）は共有ディレクトリ指定
  （`UV_INSTALL_DIR=/usr/local/bin`）を公式にサポートするが、ctx.rs のインストーラは
  単一ユーザー前提である。同じ「curl インストーラ」でも設計思想が異なるため、
  パターンはツールごとに判断する（仕様 0002 の当該記述を改訂）。
